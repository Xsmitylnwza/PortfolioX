# PortfolioX: React ownership, TSX migration, and quality gates

Date: 2026-09-24. Status: implemented and published for draft review on 2026-09-27; the opening inventory and proposed sequence below describe the pre-migration tree. Hosted PR quality passed and a non-main deploy dispatch was skipped. Production deployment was not requested.

## What the current code actually does

- Routing already exists: `AppPageRoutes.jsx` declares `/project/:id` and lazy loads `ProjectDetails.jsx`. `ProjectDetails.jsx` reads `id`, finds the record, and selects a renderer from `PROJECT_LAYOUTS` and `LAYOUT_RENDERERS`. The problem is the **lazy boundary is one shared detail chunk**, not one project renderer per case.
- `ProjectDetails.jsx` is 3,278 physical lines in the current working tree. It contains shared layouts, Keshi, Decrypt, Zucchini, FreeFlow, and ModeNote stories; Hermes and Veluma already have separate JSX modules. It statically imports all project styles, so opening one case loads the detail page's collective CSS. `App.jsx` also prewarms `ProjectDetails` after stage preparation, even on routes that never open a case.
- `src/data/projects.js` is already a small ordered registry of seven split records. `App.jsx` owns a persistent WebGL stage and transition timing; `AppPageRoutes.jsx` owns the declarative route table. The existing modularization Waves 0–5 already separated media, Veluma/Hermes layouts, project data, CSS foundations, route table, and parts of the WebGL lifecycle. The remaining active layout extraction is Wave 1d of that plan, not a restart of completed work.
- The current tree has 43 JSX, 20 JS, and 50 CSS files under `src/`. The largest active owner is `ProjectDetails.jsx`; ModeNote and FreeFlow CSS remain large but already have project owners. The Wave 5 reachability audit found 31 disconnected JS/JSX/CSS files; they need a product retain/archive decision before deletion.
- ESLint covers `src/**/*.{js,jsx}`, while `design-check.mjs`, the design scope matcher, and route mapping presently recognize JS/JSX/CSS. There is no TypeScript compiler gate. The deployment workflow runs `npm ci` then `npm run build`; it does not run lint, typecheck, or design checks. The existing design checker ratchets recorded debt and catches token and CSS ownership violations, but a build pass alone cannot establish render parity.

These observations are from static source inspection of a dirty working tree. Prior modularization reports document browser verification for earlier waves; this review did not rerun it. No current bundle-size or runtime-speed gain is claimed.

This document is the **canonical forward plan** for the remaining case extraction, TSX conversion, routing split and quality gates. The 2026-09-24 modularization plan and Wave 0–5 reports remain historical evidence and verification contracts where referenced; their old future file-placement suggestions and wave sequence do not override this sequence. Repository `AGENTS.md` controls source changes: work stays local, with no commit, push or deployment unless the owner asks. Preserve the already completed work and its route/interaction contracts.

## Target ownership

```text
src/
  app/
    App.tsx                  # persistent stage and room-transition controller
    AppPageRoutes.tsx        # top-level routes and redirects
  features/project-details/
    ProjectRoute.tsx         # small synchronous id selector, Suspense/error states
    ProjectDetailsShell.tsx  # common case shell/wave, imported by each case
    MissingProject.tsx       # invalid-id state with its needed document CSS
    projectRenderers.ts      # one module-scope lazy boundary per project id
    types.ts                 # Project and CaseLayoutProps contracts
    shared/                  # only true multi-project primitives/media/formatting
    cases/
      keshi/KeshiCase.tsx
      decrypt/DecryptCase.tsx
      zucchini/ZucchiniCase.tsx
      freeflow/FreeFlowCase.tsx
      modenote/ModeNoteCase.tsx
      veluma/VelumaCase.tsx
      hermes/HermesCase.tsx
    fallback/                # existing Cinema/Feature/Dossier compositions
  data/projects/             # existing split records and ordered gallery registry
```

This is an ownership map, not a command to rename every file at once. Keep route URL `/project/:id`, project order, missing-project behavior, gallery handoff, and the Keshi `?layout=next` preview. `AppPageRoutes` imports the small `ProjectRoute` selector synchronously; `ProjectRoute` does not import the case shell, authored case or `PROJECT_DECISIONS` copy. Case decisions stay in the lazy detail graph rather than entering the gallery bundle. Each lazy case module imports `ProjectDetailsShell` and owns its story, leaving **one dynamic JS boundary** on direct entry. Vite may place the common shell in a shared chunk; inspect the generated modulepreload/network trace to ensure this does not become a serial fetch. Keep the Cinema fallback for a future valid record with no named layout, and keep Feature/Dossier as existing extension points until a separate product decision. The renderer registry is created at module scope, pairs each explicit `() => import('./cases/keshi/KeshiCase')` loader with a stable `React.lazy` component, and shares one cached import promise with intent prefetch. Type this registry as a **partial** mapping of valid project IDs: an absent authored renderer selects Cinema. An unknown URL ID loads a small missing-project view with its own required document/case-base CSS, preserving the current visible result without importing every case style into the home bundle. The project data/order and featured IDs remain exhaustive and validated; the authored renderer mapping is intentionally not exhaustive. Do not create a computed import path, a new lazy component during render, or a second registry of project metadata.

Prefer moving files into the target folders only when their consumer and CSS ownership are clear. Shared components belong in `shared/` when at least two live cases use them, or when they hide a complex self-contained contract. Preserve `data-wave-follow`, `data-media-kind`, `data-poster-transition-target`, cursor attributes, and direct-child media relationships.

### Gate policy that applies to every wave

The one full `check:quality` command established in wave 1 is the CI/deploy gate. It reads the graph artifact produced by **that same Vite build**, checks its source hash/build ID, and fails if the artifact is missing or stale. Do not run both a raw failing legacy ESLint gate and the ratchet, or build twice through `check:design` and a separate reachability command. Keep render parity as an explicit browser/visual acceptance item for rendering changes; mechanical checks report that it remains outstanding.

Establish one-way imports: app -> feature -> shared/data; a case must not import another case or the app shell; shared must not import a case. Fail new cycles and boundary violations. Add an automated growth gate with concrete starting budgets: a **new authored UI module over 500 physical lines** or a **new function/component over 180 physical lines** fails; an existing file already above 500 lines may not grow beyond its wave-0 count, and its cap ratchets down after each extraction. A verbatim mechanical move can temporarily carry its old lines only with a machine-checked source/provenance manifest and no new behavior; the following chapter-seam slice must bring the new owner under budget. A larger cohesive-runtime exception is limited to a renderer/GL loop whose teardown must remain with its setup; authored case stories do not qualify. Exceptions live in one config with path, owner, rationale and a review trigger; inline lint disables and automatic baseline widening cannot waive the gate. Report import hops and one-user wrappers as review signals as well, because a line cap alone can be gamed. Do not auto-split on LOC: reject pass-through wrappers, duplicate registries and `utils.ts` dumping grounds.

AI change contract in `AGENTS.md`: name the owner file and affected routes before editing; keep unrelated files untouched; use existing primitives/tokens; do not add a new abstraction until two live consumers or a clear complexity boundary exists; include changed files, route impact, quality output, visual evidence for rendering changes, and remaining uncertainty in the handoff. This controls output quality without adding an owner approval checklist for every small change.
